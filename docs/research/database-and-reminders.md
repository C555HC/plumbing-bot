# База данных, управление данными и Telegram-напоминания

Исследование: 10 октября 2026 года. Ни база, ни библиотека, ни новые навыки не установлены. Ниже — объяснение и кандидаты, а не согласованный pipeline или готовая реализация.

## shadcn/ui простыми словами

shadcn/ui даёт исходники компонентов: кнопок, форм, карточек, диалогов, меню и других частей интерфейса. Код добавляется в наш проект и допускает изменение под нужды продукта. Например, из карточки, полей, списка и диалога можно собрать экран заявки сантехника.

Это интерфейсные детали; хранение клиентов, AI-команды, расписание и отправку реализует приложение. Отдельный shadcn skill помогает агенту правильно работать с этими деталями и конфигурацией проекта. Выбор компонентов и выбор навыка — разные решения.

Источник: [официальное введение](https://ui.shadcn.com/docs), [навык](https://ui.shadcn.com/docs/skills).

## Где хранится база и где появляется красивый интерфейс

Нужно различать три части: база хранит записи; административная панель помогает разработчику их просматривать; мини-ап показывает мастеру и клиенту их рабочие экраны. Панель управления базой не заменяет клиентскую CRM.

Предварительный путь данных: бот или мини-ап → серверная обработка с проверкой прав → база → нужные данные в интерфейсе. У Supabase есть и Data API для доступа из приложения при правильно настроенной авторизации и RLS; выбор конкретного пути пока открыт. Секреты административного доступа в мини-ап не передаются.

Минимальные предметные данные для обсуждения: мастера и роли, клиенты, адреса и оборудование, заявки и записи, выполненные услуги, планы обслуживания, подключение Telegram и история попыток отправки. Это перечень сущностей, а не SQL-схема. Фотографии могут храниться отдельно в файловом хранилище, а в базе — ссылки и связь с заявкой.

## Кандидаты для базы и панели

| Вариант | Что получаем | Применимость | Граница |
| --- | --- | --- | --- |
| PostgreSQL | Серверную реляционную базу для общих данных приложения | Рабочая рекомендация для сервиса нескольких мастеров и фоновых задач | Развёртывание, резервные копии и обслуживание зависят от хостинга |
| PostgreSQL в Supabase | PostgreSQL с Table Editor, SQL Editor и дополнительными сервисами | Удобный кандидат для старта с готовой панелью | Облако и собственный сервер — разные варианты эксплуатации; тариф и доступность региона не проверены |
| SQLite | Встроенную базу без отдельного сервера БД | Небольшой прототип с одним серверным приложением и низкой конкуренцией записи | Одновременно пишет один writer; несколько серверов и разделение общей файловой базы требуют иной оценки |
| pgAdmin для PostgreSQL | Официальный инструмент администрирования | Если выберем обычный PostgreSQL и нужна панель разработчику | Не интерфейс для клиента или сантехника |

**Вывод Codex:** начать выбор с PostgreSQL. Приоритет простоты управления — рассмотреть managed Supabase; при обязательном собственном сервере — обычный PostgreSQL с отдельной панелью. Самостоятельная полная установка Supabase включает больше сервисов, чем один PostgreSQL, и не является автоматически самым лёгким вариантом. SQLite не исключена для ограниченного прототипа и не считается «непригодной для сайтов».

Первоисточники: [PostgreSQL](https://www.postgresql.org/about/), [Supabase Database](https://supabase.com/docs/guides/database/overview), [Supabase Self-Hosting](https://supabase.com/docs/guides/self-hosting), [SQLite: подходящие сценарии и ограничения](https://www.sqlite.org/whentouse.html), [pgAdmin](https://www.pgadmin.org/).

## Чем отправлять напоминания

Нужны сохранённые сроки обслуживания, периодическая проверка наступивших сроков, очередь и обработчик, отправляющий сообщение через Telegram. Пример: работа 7 октября 2026 года, согласованный интервал шесть месяцев → срок 7 апреля 2027 года. Период задаётся для конкретной услуги и оборудования.

| Инструмент | Что закрывает | Граница |
| --- | --- | --- |
| pg-boss | Фоновые задачи на PostgreSQL: планирование, отложенная обработка и повторные попытки | Node.js-библиотека; Telegram-сообщение отправляет наш обработчик; MIT |
| Supabase Cron | Периодическую проверку сроков, расписание и наблюдение за запусками | Не отправитель Telegram сам по себе |
| Supabase Queues | Сохранённую очередь на PostgreSQL/pgmq | Нужен обработчик; гарантия внутри очереди не равна гарантии доставки сообщения человеку |
| Telegram Bot API + grammY | Вызовы Telegram, обработку сообщений и кнопок | TypeScript/JavaScript-вариант; грамматика AI-команд и CRM остаются нашим кодом |
| grammY auto-retry | Повтор API-запросов при 429, части серверных и сетевых ошибок | Не сохранённое полугодовое расписание; повторы ограничивать и согласовать с политикой очереди |
| grammY transformer-throttler | Ограничение темпа исходящих запросов | Дополнительный инструмент; документация предлагает сначала рассмотреть auto-retry |

**Рабочие альтернативы:** PostgreSQL + pg-boss + grammY при Node.js, либо Supabase Cron + Queues + обработчик Telegram. Не требуется одновременно выбирать две очереди. Ранее найденный aiogram остаётся альтернативой при выборе Python. Отдельный Redis в перечисленных PostgreSQL-вариантах не обязателен.

Первоисточники: [pg-boss README](https://github.com/timgit/pg-boss/blob/aa3b4f3ccb68fa610caf62ba04985deb9bc801b1/README.md), [MIT](https://github.com/timgit/pg-boss/blob/aa3b4f3ccb68fa610caf62ba04985deb9bc801b1/LICENSE), [Cron](https://supabase.com/docs/guides/cron), [Queues](https://supabase.com/docs/guides/queues), [Bot API](https://core.telegram.org/bots/api#sendmessage), [grammY auto-retry](https://grammy.dev/plugins/auto-retry), [throttler](https://grammy.dev/plugins/transformer-throttler).

## Идеи требований к надёжности

- Срок хранится в базе; перезапуск процесса не должен его терять. Долгое ожидание в памяти приложения не является нашим источником расписания.
- Долгосрочный план обслуживания остаётся источником срока; очередь обрабатывает наступившие отправки. Сроки хранения и удаления задач выбранной очереди нужно проверить отдельно, прежде чем рассчитывать на ожидание задания в течение полугода.
- Перед отправкой проверяется, не перенесено ли обслуживание, не завершена ли уже услуга и подключён ли клиент к уведомлениям.
- Задачи имеют устойчивую связь с планом обслуживания и версией срока, чтобы повторная проверка не создавала новые рассылки бесконтрольно.
- Учитываются часовой пояс и разрешённое время отправки. После простоя система отдельно обрабатывает просроченные задания по будущим согласованным правилам.
- Результаты и попытки сохраняются. Блокировка бота не должна вызывать бесконечные повторы; 429 требует ожидания.
- При сетевом тайм-ауте сообщение могло уйти, даже если ответ не получен. Telegram sendMessage не подтверждает абсолютную гарантию «ровно один раз» для нашего полного процесса; нужна политика обработки неоднозначных попыток.
- Кнопка «Записаться» ведёт к настоящей записи с проверкой доступности; клиентское напоминание не считается автоматически созданным выездом.

Для обычного бота клиент сначала должен сам открыть диалог и отправить сообщение. Контакт из Avito или телефонный номер этого не заменяют. Источники: [Telegram Bots](https://core.telegram.org/bots#how-do-bots-work), [ограничения рассылки](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).

## Найдены ли Telegram-скиллы

Найдены общественные материалы, но обязательный Telegram-навык пока не выбран:

- [HACODE-SOLUTIONS/telegram-bot-starter](https://github.com/HACODE-SOLUTIONS/telegram-bot-starter) описывает Node/grammY-шаблон, webhook/polling и инструкции для агентов. Кандидат для примера запуска, не подтверждённая готовая CRM или система повторных услуг. README просмотрен; полный SKILL.md и работа шаблона не проверены, снимок коммита получить не удалось из-за сетевого тайм-аута.
- [hec-ovi/telegram-bot-skill](https://github.com/hec-ovi/telegram-bot-skill/tree/4e2e196b1984d6652fc78b6d508184094a428f78) соединяет Telegram с локальным CLI-агентом. Для нашей клиентской CRM предметно не подходит как основа напоминаний.

**Вывод:** для отправки полезнее прежде всего документация Telegram и проверенные библиотеки/очередь. Позднее можно оформить короткий проектный навык для правил уведомлений; сейчас он не создан.
